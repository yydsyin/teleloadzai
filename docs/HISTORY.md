## 3. Locked decisions (v1)

| # | Decision |
|---|---|
| 1 | Project name: **Teleloadzai**. The name lives in **one config constant** so renaming stays cheap. |
| 2 | **Windows only for v1.** macOS / Linux come later. |
| 3 | Base engine: **yt-dlp + ffmpeg**. Both are managed by us — never assume they exist on the machine. |
| 4 | Specialist tools **only** where yt-dlp is weak. Do not add a tool "just in case". |
| 5 | **The installer asks which sites you use**, and installs only the tools they need (step 6). *(Changed by the user 2026-09-26. Until then: "First launch = platform picker", inside the app — see decision 17 for why it moved.)* |
| 6 | Safety net = **install on demand**. Never answer "not supported" if a tool exists — offer to install it and continue. |
| 7 | A **Tools page** in settings: installed / not installed / update available. The user can add or remove any tool, any time. |
| 8 | **Auto-update check on start**, in the background, never blocking. "Update all" button always visible. When a download fails, suggest updating **first** — as advice, not as a cause (decision 38). ⚠️ *Corrected 2026-10-18 (grids): this line said "that is the cause ~80% of the time"; that number was never measured.* ➕ 2026-09-27: Update is offered only when a newer version exists (the versions are loaded at start; unknown keeps it offered). ➕ **2026-10-21: "Update all" is built** — in the bar at start and in Settings → Programs (called Tools until 2026-10-23; promised here since 2026-09-20, never built until then). A failed download asks GitHub at once, and its row offers **"Update <tool> and retry"**; "updated" is said only when the version read from the tool really changed. |
| 9 | **Cookies supported but OFF by default. The user never types a password into Teleloadzai.** That much has never changed. ⚠️ **The mechanism has.** This line said "read from the browser (`--cookies-from-browser`)" from 2026-09-20 until the 2026-09-22 audit found the flag appears **nowhere** in the code except inside a quoted error message. It was never written, because it does not work: all four browsers on the developer's PC refused, and **Brave refused while closed** — Chromium now seals its cookies with a key Windows returns only to the browser itself (yt-dlp issue 10927, still open, and yt-dlp is already the newest version). The two roads that exist are decision 36's: **log in inside the app**, or **import a `cookies.txt`**. Reading the browser stays possible one day, for machines that allow it; it is not what we do. |
| 10 | **No DRM platforms.** Netflix, Disney+, Prime Video, Spotify, paid course sites: out of scope, permanently. |
| 11 | Stack: **Python backend + local web UI**, shipped as a **.zip on GitHub Releases**. The user must not need to install Python. |
| 12 | **Open source on GitHub.** |
| 13 | **The user can change the tool.** Every platform has a Teleloadzai default, but the user may override it. Two levels: **per platform** (settings, permanent) and **per download** (one time, from the main window). Only tools that actually support that platform are offered. *(The per-platform level was written in this table on 2026-09-20 and built only on 2026-09-24 — Settings → "Tool for each site", shown only for sites with more than one usable tool; since 2026-10-23 **Settings → Sites**, one row per site with its program and its log-in, a switch of program names where there is a choice. A saved choice that is no longer usable is ignored, never obeyed into a dead end.)* ➕ **2026-09-26, after the critique:** when the default's need is a proven **log-in** (`login._NEEDS` kind "login") and that log-in is missing, the card **starts on another installed tool that needs none**, and says so: *"Using yt-dlp: gallery-dl, the usual tool for Instagram, needs you to be logged in to Instagram."* with the log-in button. After the log-in it goes back to the default. **The default itself does not change**, a "visit" need never moves it (TikTokDownloader often works without one, with the better picture), and a tool the user presses always stands. Seen in the app: Instagram → yt-dlp; TikTok and Kuaishou unchanged. ➕ **2026-09-26, the user's decisions after the review loop:** *(1)* **the switch keeps the program names** ("TikTokDownloader \| yt-dlp") — the reviews asked for results instead ("Higher quality \| Smaller file"); decided, not to be reopened; the result is said in words under it ("TikTokDownloader: higher quality."). *(2)* **The format can choose the tool:** MP3 shows whenever any tool of the site makes one; pressed on a tool that makes none (gallery-dl on Weibo), the card moves to the one that does and says *"Chosen for the MP3 — gallery-dl makes none."*; MP4 gives the tool back; a tool picked by hand stands. Seen: the job went to yt-dlp, MP3, 128 kbps (call intercepted, nothing downloaded). *(3)* **The Quality list comes from the video's real sizes.** ⚠️ **Corrected 2026-09-27:** the first version took the tallest picture the site *lists* and wrote it on "Best" — TikTok lists 720p, the download rule (a real .mp4 first) gave **1024×576**, and its "480p" gave the same 576p file (ffprobe, 18,277,961 bytes). Worse, **TikTok answers 720p to one request and 576p to the next** (3 of 5 / 2 of 5), so no number read beforehand can be promised. Now the title read asks yt-dlp with the download's own rule (`ytdlp._MP4_BEST`), "Best" carries **no number**, and a smaller size is offered **only if the video has that exact height**: TikTok → no list; Bilibili "Best, 720p, 480p, 360p"; the test stream "720p, 480p" (no 360p: it has none), and 480p gave **848×480**. Nothing is offered while the title is read or when it could not be read. The MP3 list stays whole (our own FFmpeg settings, measured). |

| 18 | **Update check before every use, but cached.** Store per tool: last check time + last known version. Before running a tool: note fresher than 24 h -> start at once; note older -> ask GitHub (1 request), then act. A site that breaks gets its fix in yt-dlp within hours; 24 h was too slow. |
| 19 | **Default update mode = "Ask me first"** — a bar with `[Update now] [Later]`. The user can switch to *Automatic* or *Manual* in settings. **Never update while a download is running**: update before starting, or when the queue is empty. 🔄 **Changed by the user 2026-10-21, and built that day:** a tool is never updated **while it is downloading** — that tool waits ("waits for 1 download to finish"), its new downloads wait for the update, the other tools are not blocked (FFmpeg serves every download, so it waits for all). The three modes are a setting: **Ask me first** (the bar, and "Update and retry"), **Automatic** (updates at start, and a failed download is updated and retried **once**), **Manual** (only the badges). **yt-dlp's preview channel** is a second setting, Stable by default; a failed yt-dlp row offers it when stable is already the newest. Seen in the app with real yt-dlp releases (2026.07.04 → 2026.08.19, the preview 2026.10.10.233141 and back). |
| 20 | **Standard library only, with ONE exception.** The server is `http.server`, the UI is one HTML file. The only pip package allowed is `pywebview` (decision 25). Every new dependency must be asked for. |
| 21 | **The local server is locked down**: it listens on `127.0.0.1` only, refuses any `Host` that is not localhost, and every `/api/` call must carry a secret token created at startup. Without this, any web page open in the browser could drive Teleloadzai. ➕ **2026-09-27: the port is ours alone** (`SO_EXCLUSIVEADDRUSE`, `server.claim`), **taken before anything else runs.** Python's server asks for "reuse address", which on Windows let a second copy take 8777 with no error (netstat: 2 listeners) — and that copy ran "forget the log-ins" at start, under the first copy's feet. Now a second copy says *"Teleloadzai is already open"* (a Windows box and the console) and exits; a port held by another program is said as such. |
| 22 | **"Save as" window, ON by default.** When a link is added, the Windows "Save as" dialog opens: the user picks the folder AND the file name, and Windows itself asks before replacing. A setting turns it off (save straight to the folder). ➕ **2026-10-24:** several links pasted at once get **one** folder window for all (the user's choice), never one "Save as" per link — Phase 2 item 1. ➕ **2026-10-24, later the same day: the user's mode decides.** "Same for all" keeps the one folder window; **"Choose for each"** gives **one window per video** (the user asked for "one by one"). And a program that names its files itself (`runners.NAMES_ITSELF`: gallery-dl, XHS-Downloader in MP4) is asked a **folder**, never a name — its "Save as" name was thrown away, on the one-link card too. |
| 23 | **The dialog runs when the job is ADDED, never when it starts.** Otherwise a queue left alone would stop and wait for a window nobody is watching. |
| 24 | **Never a success that did not happen, and never a silent overwrite.** Two roads: *(a)* the user picked a path in the "Save as" window — Windows already asked about replacing, so yt-dlp gets `--force-overwrites`; *(b)* the user is **not** asked (`ask_where` off) — then nothing may be destroyed behind his back. After the run we compare each file's date with the start time; if it was not rewritten, the job says **"already there — nothing was downloaded"** (grey, not green) with a `Download again` button that forces it. ⚠️ Found on road (a) the 2026-09-20 and announced as fixed; the §2.4 audit found it **still alive on road (b)** the 2026-09-21. A fix on one path is not a fix. ➕ **2026-09-26, the same defect on the specialist tools:** with "Save as" off, a TikTok / Douyin / Kuaishou MP3 or MP4 wrote straight onto a file of the same name, and FFmpeg's `-y` replaced an MP3 of the user's. Now road (b) holds for them too (`runners._already_there`): the row says *"… is already in this folder"* with `Download again`. Checked with the check switched off (the user's file replaced), then on (unchanged), and in the app (skipped, then replaced by `Download again`). ➕ **2026-09-27, a post of several items:** yt-dlp ignores `--no-playlist` on Instagram ("Downloading 3 items of 3") and wrote the 3 videos under **one name** — with "Save as" each overwrote the last (the user got video 3), without it videos 2 and 3 were skipped (he got video 1), and the row said *done* while the card promised "only the first one". Now each item is numbered, "name 1", "name 2"… (a single video gets none), and `--force-overwrites` is given only when no numbered file is there, so it can only replace the name Windows asked about (`ytdlp._only_chosen_name`). Seen: Post 1/2/3 = 39,753 / 2,524,830 / 960,393 bytes; run again, nothing replaced and "already there". |

| 34 | 🚨 **A problem is always said, never swallowed.** Every failure reaches the user in plain words: which step, what happened, what he can do. Silence is the worst answer — it cannot be told apart from a frozen app. *(Counted 2026-09-22: 16 places catch an error and return silence. Three are user-visible: a short link that cannot be followed is never shown — `redirect_error` exists in the code and appears **0 times** in the page; a failed repackaging keeps the `.ts` and says nothing; a Windows dialog that errors looks exactly like the user pressing Cancel.)* ⚠️ Catching an error to keep the app alive is right. Catching it to keep the user ignorant is not. ➕ **2026-09-26, Stop did not stop.** `yt-dlp.exe` and `streamlink.exe` are **launchers** that start the real program as a second process; Stop terminated the launcher only. Seen: a job stopped after 10 s kept downloading unseen and delivered the whole 164,088,517-byte file, and the row said *stopped*. `jobs.stop_tree()` now ends the whole family (`taskkill /T` while the launcher is alive): 0 processes left, the file frozen, checked in the real app; gallery-dl, N_m3u8DL-RE and XHS-Downloader are single processes, also 0 left. A stopped yt-dlp job then removes **only its own** unfinished pieces — the names yt-dlp announced for that job (`Destination:`), their `.part` / `.ytdl` / `.part-FragN`, and a picture-only / sound-only piece only if written after the job started; checked with two traps in the folder (another job's `.part`, an old look-alike), both kept. ➕ **2026-09-26, a title nobody could read is said, and the file is named "unknown"** (asked by the user). The card says *"No title found"*, why, and what the file will be called on the road chosen. | 36 | 🚨 **Logging in happens INSIDE Teleloadzai. The exported file is the second road, not the first.** A window opens on the site, the user logs in as he always does, and we take that site's cookies from our own WebView2 window — `httpOnly` ones included, which an export often misses. **The reason is not comfort: a browser export hands us every site the user is logged into; a log-in hands us one.** yt-dlp's own FAQ warns where such a file must not end up. *(Decided 2026-09-22 after the user asked why no other downloader works the way ours did. Parabolic, the leading open-source front end, does use a file — and nobody in its feature request proposed anything else. 4K Video Downloader Plus opens the site in-app, and that is the one he had seen.)* ⚠️ Three things only running it revealed, all kept in `login.py`: read the cookies on the **platform's own page**, never where the log-in finished, or YouTube hands us `.google.com` and with it a Gmail session · a WebView2 date in the past means **session cookie**, not expired · **"Forget them" must really forget** — Windows locks the profile while the app runs, so a refused deletion is carried out at the next start. ➕ **2026-09-23/24: the window finishes by itself.** The user asked not to come back and press a button. It closes once the window has left the log-in page for the site itself, or — where the log-in is a pop-up that never changes the address — once a cookie that only exists when logged in appears (seen on a real log-in only: Kuaishou's `userId`). Closing it by hand keeps what it had; before, that took **nothing and said nothing**. Three lessons, each seen: Kuaishou's separate passport page **never goes back** to the site after a QR scan — its real log-in is a pop-up we open by pressing the site's own button · **X and Archive.org move their own log-in page** on arrival, and the window closed itself before anyone logged in, so an address that still says *login* never counts as "past it" · WebView2 gives the cookies **of the page the window is on**, so the window is taken back to the site's main address before reading. ➕ **2026-09-25, logging in through Facebook or Google:** *(1)* pywebview sends every new window to the PC's default browser, so "Continue with Facebook" opened **Chrome**, whose cookies nobody can read. For the log-in window only, the new window is left to **WebView2's own pop-up**: same profile, and still **tied to the page that opened it**. ⚠️ Loading it **in place of** the page does not work — seen: Facebook opened, could no longer answer TikTok, and the user stayed stuck on Facebook. *(2)* **A log-in keeps only the chosen site's cookies.** The general filter, made for an imported file, keeps every site we download from; a TikTok log-in through Facebook had left three facebook.com cookies (not a session, but the next ones could be). *(3)* **Each log-in button shows a sign**, asked by the user: **green, red, or nothing — never a grey "maybe"** (the grey lived one day and the user did not know what it meant). The sign reads the site's **badge**: the one cookie a site hands only to a logged-in user. Green = the badge is in our file; red = past its end date; nothing = no badge. Badge names come **only from evidence** (decision 38): yt-dlp's own "is this user logged in?" code (source of 2026-09-16, read 2026-09-25) for YouTube, Bilibili, TikTok, Instagram, X, Reddit, Twitch, Niconico — and the user's real log-in for Kuaishou. The other sites have no known badge: green only when the log-in window saw the log-in finish. Said in words too, never by colour alone. ⚠️ Found by reading the badges: **TikTok was green with no `sid_tt` in the file** — the window had finished, the user was not logged in. A finished window is not proof when a badge can be read. ⚠️ Red is **about the date only**: a site that ends a session early (a log-out elsewhere) cannot be seen from here, and a badge **with no date** (Kuaishou's) never turns red — only asking the site could tell, not done. *(4)* A site refused later (Netflix) **loses the cookies it already had**: the filter guarded only what came in, and 5 netflix.com cookies were still in the user's file. They are now removed at every start. ➕ **2026-09-26: a proven log-in cookie is the ONLY sign to close.** For the 10 sites whose log-in cookie is proven (the badges above, Douyin and Kuaishou included), the window closes when that cookie appears and never because the address changed — "left the log-in page" had closed TikTok's window with no `sid_tt`. The address rule stays only for the 13 sites with no proven cookie yet (checked with a fake window: TikTok leaving `/login` without `sid_tt` stays open; with TikTok taken off the list, the old false close came back). **Douyin:** its log-in cookies are `sessionid` / `sid_tt` — recorded on the user's own QR log-in, names only, every 2 s: 33 cookies from the visit and the QR pop-up, then 18 at once at the log-in. Before that, Douyin's window had no sign at all and never closed by itself. Its QR pop-up **opens by itself** 14–32 s after the page (6 runs of 6, with a control run that pressed nothing); scripted clicks on its 登录 button and on the pop-up's close icon changed nothing — so nothing is pressed, and the log-in message says to wait. ⚠️ **Corrected the same day:** the log-in window runs in pywebview's **private mode** (its default: *"cookies and local storage are not preserved"*), so `data/login-profile` never holds a log-in — its cookie database was found empty. Log-ins live only in `data/cookies.txt`; the "locked profile" lines above are about caches, not cookies. It also means each log-in window starts logged out. ➕ **2026-09-28: one rule for "logged in"** (`login._sign`), used by the Settings sign **and** the download card. The card read only the badge, so Vimeo (no known badge, the log-in window saw it finish) was green in Settings while its card said "log in", after a title read that had already used the log-in.
